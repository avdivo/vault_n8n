# VaultN8N

VaultN8N — это минималистичное серверное приложение для безопасного хранения, выдачи и удаления секретов (паролей, токенов и т.п.) через HTTP API. Оно разработано для интеграции с [n8n](https://n8n.io/) или для использования в качестве простого и легковесного хранилища секретов.

Проект создан с упором на простоту, предсказуемость, минимальные зависимости и небольшой размер Docker-образа.

## Почему VaultN8N: минимализм без компромиссов с безопасностью

На рынке существует множество решений для хранения секретов — от enterprise-систем вроде HashiCorp Vault до облачных сервисов (AWS Secrets Manager, Azure Key Vault). Но все они рассчитаны на масштабные инфраструктуры и требуют значительных ресурсов. VaultN8N создан для другой аудитории: тех, кто ценит простоту, предсказуемость и минимальный «цифровой след».

### Реальное потребление ресурсов

| Параметр                | VaultN8N | HashiCorp Vault* | AWS Secrets Manager** |
|-------------------------|----------|------------------|-----------------------|
| **Размер Docker-образа** | **16 МБ** | 200+ МБ          | — (сервис)            |
| **Потребление RAM**      | **~65 МБ** | 256+ МБ          | — (сервис)            |
| **Зависимости**          | Python + SQLite | Consul, TLS, PKI | API + IAM             |
| **Время запуска**        | < 3 сек  | 15–30 сек        | —                     |

> *Для минимальной рабочей конфигурации Vault в dev-режиме  
> **Плата за запросы + сложность интеграции через IAM

### Для кого этот проект?

- **Индивидуальные разработчики и фрилансеры**, использующие n8n для автоматизации
- **Небольшие команды** с простыми потребностями в хранении секретов
- **Владельцы бюджетных VPS** (512 МБ–1 ГБ RAM), где каждый мегабайт на счету
- **Энтузиасты и хобби-проекты** на Raspberry Pi или старом железе
- **Те, кто устал** от сложности настройки полноценного Vault ради трёх API-ключей

### Что вы получаете

- **Настоящее шифрование**: данные хранятся в SQLite, зашифрованные через AES-256-GCM с аутентификацией. Без `ENCRYPTION_KEY` содержимое `secrets.db` — мусор.
- **Мгновенный запуск**: один скрипт развёртывает всё — от генерации ключей до работающего контейнера.
- **Нативная интеграция с n8n**: достаточно узла *HTTP Request* + Bearer-токен — никаких плагинов или сложных настроек.
- **Предсказуемость**: нет фоновых процессов, ротации ключей, кластеризации — только то, что нужно для хранения и выдачи секретов.
- **Портативность**: весь стек — один контейнер, один файл БД, один `.env`. Легко переносится, резервируется и восстанавливается.

### Что вы *не* получаете (и это осознанный выбор)

- Аудит операций
- RBAC и управление ролями
- Автоматическую ротацию ключей
- Кластеризацию и отказоустойчивость

Это не недостатки — это границы применения. VaultN8N не претендует на роль корпоративного хранилища. Он решает одну задачу — **надёжно хранить несколько десятков секретов с минимальными накладными расходами** — и решает её предельно просто.

### Где это работает

- Бюджетный VPS (Hetzner, DigitalOcean от $4/мес)
- Raspberry Pi 3/4 в домашней лаборатории
- Общий сервер с n8n без дополнительной нагрузки
- Локальная разработка с сохранением секретов между перезапусками

Минимализм — не слабость. Это осознанный выбор для тех, кому не нужны 90% функций тяжеловесных решений ради 10% реальной задачи.

## Сценарии использования с n8n

`VaultN8N` создан как раз для того, чтобы элегантно решать некоторые задачи, с которыми сталкиваются пользователи n8n. Вот несколько практических сценариев:

#### 1. Управление секретами для нескольких клиентов или проектов
Если вы используете один экземпляр n8n для автоматизации задач нескольких клиентов, `VaultN8N` поможет навести порядок и повысить безопасность.
- **Проблема:** Все API-ключи, токены и пароли от разных клиентов хранятся вперемешку в стандартном менеджере учетных данных n8n.
- **Решение:** Храните секреты каждого клиента в `VaultN8N` под уникальными ключами (например, `client_A_google_token`). Ваш workflow в n8n перед выполнением основной логики делает простой HTTP-запрос, забирает нужный ключ и использует его. Это обеспечивает изоляцию и порядок.

#### 2. Динамическое обновление токенов
Многие сервисы (особенно по OAuth2) выдают токены доступа с ограниченным сроком действия.
- **Проблема:** Стандартные учетные данные n8n не всегда могут автоматически обновлять такие токены.
- **Решение:** Создайте отдельный workflow в n8n, который по расписанию получает новый токен и сохраняет его в `VaultN8N`. Остальные workflow просто забирают актуальную версию токена оттуда. Это разделяет логику обновления токена и его использования.

#### 3. Безопасное хранение workflow в Git (GitOps-подход)
При хранении JSON-файлов рабочих процессов в Git нельзя «зашивать» в них реальные пароли.
- **Проблема:** Жестко закодированные учетные данные в файлах — это огромная дыра в безопасности.
- **Решение:** Вместо реального токена используйте в узлах n8n ссылку на ключ в `VaultN8N`. Workflow будет динамически получать секрет во время выполнения. Таким образом, в Git хранится только "рецепт" workflow, а не его чувствительные данные.

#### 4. Централизованное хранилище для нескольких сервисов
Если у вас есть не только n8n, но и другие скрипты или приложения, `VaultN8N` может стать единым источником правды для секретов.
- **Проблема:** Как безопасно поделиться паролем от базы данных между n8n и сторонним Python-скриптом?
- **Решение:** И n8n, и ваш скрипт могут обращаться к `VaultN8N` по API за нужными секретами.

#### 5. Работа на слабых устройствах (Raspberry Pi, дешевые VPS)
`VaultN8N` очень легковесный, что делает его идеальным выбором для систем с ограниченными ресурсами.
- **Проблема:** Запускать полноценный HashiCorp Vault на сервере с 1 ГБ оперативной памяти практически невозможно.
- **Решение:** `VaultN8N` потребляет минимум ресурсов, не нагружая вашу систему, где уже работает n8n.

## Установка и запуск

Существует два основных способа запуска приложения: быстрый старт для обычных пользователей и запуск для разработчиков.

### Быстрый старт для пользователей (рекомендуется)

Этот способ не требует клонирования репозитория и идеально подходит для быстрого развертывания. Все, что вам нужно — это установленный `Docker`, `docker-compose` и `curl`.

1.  **Выполните команду в терминале:**

    ```bash
    curl -sSL https://raw.githubusercontent.com/avdivo/vault_n8n/main/start.sh | bash
    ```

    > ✨ **Важно:** При первом запуске скрипт сгенерирует и выведет в консоль `VAULT_N8N_AUTH_TOKEN` и `VAULT_N8N_ENCRYPTION_KEY` в специальных рамках. **Обязательно скопируйте эти значения и сохраните их в надежном месте.** Эти данные также будут автоматически сохранены в файл `.env` в текущей директории для последующих запусков. Учтите, что без `VAULT_N8N_ENCRYPTION_KEY` вы не сможете расшифровать ранее сохраненные секреты.

2.  **Что сделает этот скрипт?**
    *   **Создаст директорию `vault_n8n`** (если ее нет) для инкапсуляции файлов проекта.
    *   Скачает последнюю версию `docker-compose.yml` из репозитория **в директорию `vault_n8n`**.
    *   Проверит, существует ли **в родительской директории** файл `.env`. Если нет — создаст его.
    *   Проверит, заданы ли в `.env` ключи `VAULT_N8N_AUTH_TOKEN` и `VAULT_N8N_ENCRYPTION_KEY`. Если нет — сгенерирует их и добавит в файл.
    *   **Создаст пустой файл `vault_n8n/secrets.db`** (если его нет) для хранения секретов.
    *   Запустит последнюю версию приложения из [Docker Hub](https://hub.docker.com/r/avdivo/vault-n8n).

3.  **Готово!**
    Ваше приложение запущено. Необходимые для доступа `VAULT_N8N_AUTH_TOKEN` и `VAULT_N8N_ENCRYPTION_KEY` сохранены в файле `.env` в той же директории, откуда вы запускали скрипт. Сохранность этого файла обеспечивает сохранность ваших данных.

### Запуск для разработки

Этот способ предназначен для тех, кто хочет вносить изменения в код.

1.  **Клонируйте репозиторий:**
    ```bash
    git clone https://github.com/avdivo/vault_n8n.git
    cd vault_n8n
    ```

2.  **Запустите скрипт для разработки:**
    ```bash
    ./start-dev.sh
    ```
    > ✨ **Важно:** При первом запуске скрипт сгенерирует и выведет в консоль `VAULT_N8N_AUTH_TOKEN` и `VAULT_N8N_ENCRYPTION_KEY` в специальных рамках, если они отсутствуют в файле `.env`. **Обязательно скопируйте эти значения и сохраните их в надежном месте.** Учтите, что без `VAULT_N8N_ENCRYPTION_KEY` вы не сможете расшифровать ранее сохраненные секреты.
    
    Этот скрипт автоматически подготовит `.env` файл (аналогично пользовательскому скрипту) и запустит `docker-compose`, но **соберет образ из локальных исходников**, что позволит вам сразу видеть ваши изменения.

3.  **Альтернативный ручной запуск (без Docker):**
    Если вы хотите запускать приложение напрямую для отладки:
    ```bash
    # Создайте и активируйте виртуальное окружение

    source venv/bin/activate

    # Установите зависимости

    # Убедитесь, что .env файл существует (можно запустить ./start-dev.sh один раз)

    # Запустите приложение

    ```
    После запуска приложение будет доступно по адресу `http://localhost:8200`.

## Конфигурация


Приложение конфигурируется через переменные окружения, которые автоматически создаются в файле `.env` при первом запуске с помощью скриптов.

-   **`VAULT_N8N_AUTH_TOKEN`**: (Обязательно) Секретный токен для авторизации доступа к API.
-   **`VAULT_N8N_ENCRYPTION_KEY`**: (Обязательно) 64-символьный hex-ключ для шифрования данных.
-   **`DATABASE_PATH`**: (Опционально) Путь к файлу базы данных SQLite. По умолчанию: `./secrets.db`.

### `POST /api/v1/secrets/single`

**Назначение:** Создание или обновление одного секрета. Если секрет с указанным ключом уже существует, его значение будет перезаписано.

**Входные данные (JSON Body):**
```json
{
  "key": "my_service_password",
  "value": "super_secret_password_123"
}
```

**Пример запроса:**
```bash
curl -X POST "http://localhost:8200/api/v1/secrets/single" \
     -H "Content-Type: application/json" \
     -H "Authorization: Bearer $VAULT_N8N_AUTH_TOKEN" \
     -d '{ "key": "my_service_password", "value": "super_secret_password_123" }'
```

**Пример успешного ответа (JSON):**
```json
[
  {
    "key": "my_service_password",
    "value": "super_secret_password_123"
  }
]
```

---

### `POST /api/v1/secrets/bulk`

**Назначение:** Массовое создание или обновление нескольких секретов.

**Входные данные (JSON Body):** Массив объектов, каждый из которых представляет секрет.
```json
[
  { "key": "api_key_prod", "value": "prod_api_token_xyz" },
  { "key": "db_user", "value": "admin_user" }
]
```

**Пример запроса:**
```bash
curl -X POST "http://localhost:8200/api/v1/secrets/bulk" \
     -H "Content-Type: application/json" \
     -H "Authorization: Bearer $VAULT_N8N_AUTH_TOKEN" \
     -d '[ { "key": "api_key_prod", "value": "prod_api_token_xyz" }, { "key": "db_user", "value": "admin_user" } ]'
```

**Пример успешного ответа (JSON):**
```json
[
  {
    "key": "api_key_prod",
    "value": "prod_api_token_xyz"
  },
  {
    "key": "db_user",
    "value": "admin_user"
  }
]
```

### `GET /api/v1/secrets`

**Назначение:** Получение одного или нескольких секретов по ключам.

**Входные данные (Query-параметр):**
- `keys`: Строка, содержащая один или несколько ключей, разделенных запятыми.
- **Фильтрация по маске:** Вы можете использовать символ `*` в качестве wildcard для поиска по шаблону.

**Примеры использования параметра `keys`:**
- `?keys=my_secret_key` — найти один конкретный ключ.
- `?keys=key1,key2,key3` — найти три конкретных ключа.
- `?keys=service_A_*` — найти все ключи, начинающиеся с `service_A_`.
- `?keys=key1,service_B_*` — найти ключ `key1` и все ключи, начинающиеся с `service_B_`.

**Пример запроса:**
```bash
curl -X GET "http://localhost:8200/api/v1/secrets?keys=my_service_password,api_key_*" \
     -H "Authorization: Bearer $VAULT_N8N_AUTH_TOKEN"
```

**Пример успешного ответа (JSON):**
(Возвращаются только найденные секреты)
```json
[
  {
    "key": "my_service_password",
    "value": "super_secret_password_123"
  }
]
```

---

### `DELETE /api/v1/secrets`

**Назначение:** Удаление одного или нескольких секретов по ключам или маске.

**Входные данные (Query-параметр):**
- `keys`: Строка, содержащая один или несколько ключей/масок для удаления (правила те же, что и для `GET`).

**Пример запроса:**
```bash
curl -X DELETE "http://localhost:8200/api/v1/secrets?keys=db_user,api_key_prod" \
     -H "Authorization: Bearer $VAULT_N8N_AUTH_TOKEN"
```

**Пример успешного ответа (JSON):**
(В ответе возвращаются удаленные секреты)
```json
[
  {
    "key": "db_user",
    "value": "admin_user"
  },
  {
    "key": "api_key_prod",
    "value": "prod_api_token_xyz"
  }
]
```

### Обработка ошибок

API использует стандартные HTTP-статус-коды для информирования об ошибках.

**`401 Unauthorized`**
- **Причина:** Неверный или отсутствующий `VAULT_N8N_AUTH_TOKEN`.


**`422 Unprocessable Entity`**
- **Причина:** Ошибка валидации входных данных. Например, отсутствует обязательное поле в теле запроса, неверный тип данных или невалидный JSON.
- **Пример ответа (неверное тело в `POST /secrets/single`):**
  ```json
  {
    "detail": [
      {
        "loc": [
          "body",
          "key"
        ],
        "msg": "field required",
        "type": "value_error.missing"
      }
    ]
  }
  ```

**`500 Internal Server Error`**
- **Причина:** Непредвиденная ошибка на стороне сервера (например, проблема с доступом к базе данных).
- **Пример ответа:**
  ```json
  {
    "detail": "Внутренняя ошибка сервера: <описание_ошибки>"
  }
  ```
> Примечание: в production-среде детальное описание ошибки может быть скрыто из соображений безопасности.

## Интеграция с n8n

Для взаимодействия с VaultN8N из n8n используется узел **HTTP Request**.

> **URL сервиса:** Если n8n и VaultN8N запущены в одной `docker-compose` сети, то для обращения к VaultN8N используйте имя сервиса как хост. Порт указывать не нужно, так как сервисы общаются по внутренним адресам. Корректный базовый URL будет `http://vault_n8n/api/v1`. В противном случае, используйте внешний IP-адрес или домен с портом (например, `http://ваш_домен:8200/api/v1`).

### Настройка авторизации

Авторизация настраивается один раз и используется для всех запросов.

1. В узле `HTTP Request` выберите:
  - **Authentication:** `Generic Credential Type`
  - **Generic Auth Type:** `Header Auth`
  - **Header Auth:** `Header Auth account`  
2. Нажмите `Create New Credential`.
3. В открывшемся окне:
  - **Name:** `Authorization`
  - **Value:** Вставьте `Bearer ваш_токен` (например, `Bearer my_secret_token_from_env_file`). **Важно:** Не забудьте написать слово `Bearer` и пробел перед самим токеном.

### Примеры настройки узла HTTP Request
    > ✨ **Внимание:** Для методов GET, DELETE параметры указываются в разделе `Send Query Parameters`, а для POST в `Send Body`.
#### 1. Добавление/Обновление одного секрета

- **Method:** `POST`
- **URL:** `http://vault_n8n/api/v1/secrets/single`
- **Body Content Type:** `JSON`
- **JSON:**
  ```json
  {
    "key": "n8n_secret_key",
    "value": "n8n_secret_value"
  }
  ```
  Вы также можете использовать выражения n8n для динамической подстановки значений:
  ```json
  {
    "key": "={{ $json.some_key }}",
    "value": "={{ $json.some_value }}"
  }
  ```

#### 2. Массовое добавление/обновление секретов

- **Method:** `POST`
- **URL:** `http://vault_n8n/api/v1/secrets/bulk`
- **Body Content Type:** `JSON`
- **JSON:**
  ```json
  [
    { "key": "api_key_prod", "value": "prod_api_token_xyz" },
    { "key": "db_user", "value": "admin_user" }
  ]
  ```

#### 3. Получение секретов

- **Method:** `GET`
- **URL:** `http://vault_n8n/api/v1/secrets`
- **Options -> Query Parameters:**
  - Нажмите `Add Parameter`.
  - **Name:** `keys`
  - **Value:** `n8n_secret_key,api_key_*` (можно указывать несколько ключей и маски).

#### 4. Удаление секретов

- **Method:** `DELETE`
- **URL:** `http://vault_n8n/api/v1/secrets`
- **Options -> Query Parameters:**
  - Нажмите `Add Parameter`.
  - **Name:** `keys`
  - **Value:** `n8n_secret_key`

## Интеграция с проектом n8n-install

Для добавления сервиса `vault-n8n` в вашу инсталляцию `n8n-install` (проект [kossakovsky/n8n-install](https://github.com/kossakovsky/n8n-install)) выполните в корневой директории проекта `n8n-install` следующую команду:

```bash
curl -sSL https://raw.githubusercontent.com/avdivo/vault_n8n/main/add_to_kossakovsky-n8n-install.sh | bash
```

При первом запуске скрипт сгенерирует и выведет в консоль данные для доступа.

### Что делает скрипт?

Скрипт автоматически и безопасно вносит следующие изменения в ваш проект `n8n-install`:

1.  **Создает директорию `./vault-n8n/`**: В ней будут храниться все файлы, относящиеся к сервису.
2.  **Добавляет переменные в `.env`**: В конец вашего основного `.env` файла будут добавлены переменные, необходимые для работы сервиса (`VAULT_N8N_HOSTNAME`, `VAULT_N8N_AUTH_TOKEN`, `VAULT_N8N_ENCRYPTION_KEY`).
3.  **Создает Docker-конфигурацию**: В директории `./vault-n8n/` будет создан файл `docker-compose.vault-n8n.yml`, описывающий, как запускать контейнер.
4.  **Обновляет `Caddyfile`**: В конфигурацию вашего веб-сервера Caddy будет добавлен новый блок для предоставления внешнего доступа к `vault-n8n` по адресу `http://vault-n8n.ваш-домен`.
5.  **Создает управляющий скрипт `./vault.sh`**: Для удобного запуска и остановки контейнера.

### Важные замечания

*   ⚠️ **Сохраните ключи!** При первом запуске скрипт сгенерирует `VAULT_N8N_AUTH_TOKEN` и `VAULT_N8N_ENCRYPTION_KEY`. **Обязательно сохраните их в надежном месте.** Без `ENCRYPTION_KEY` вы не сможете в будущем расшифровать сохраненные секреты.
*   ✅ **Безопасность повторного запуска**: Скрипт можно безопасно запускать повторно. Он не перезапишет уже существующие ключи в `.env` файле и не удалит базу данных.
*   **Расположение файлов**:
    *   **Файл конфигурации Docker**: `./vault-n8n/docker-compose.vault-n8n.yml`
    *   **База данных (SQLite)**: `./vault-n8n/data/secrets.db`

## Публикация новой версии

Этот проект использует [GitHub Actions](https://github.com/features/actions) для автоматической сборки и публикации Docker-образа в [Docker Hub](https://hub.docker.com/).

Публикация новой версии происходит при создании и отправке в репозиторий нового Git-тега, соответствующего формату `v*.*.*` (например, `v1.0.0`, `v1.2.3`).

**Порядок действий для выпуска новой версии:**

1.  Убедитесь, что все последние изменения находятся в ветке `main`.
2.  Создайте новый тег, следуя принципам [семантического версионирования](https://semver.org/lang/ru/).
    ```bash
    # Пример создания тега для версии 1.0.1
    git tag v1.0.1
    ```
3.  Отправьте тег в удаленный репозиторий.
    ```bash
    git push origin v1.0.1
    ```
4.  После этого GitHub Actions автоматически запустит процесс сборки и публикации.

## Советы по безопасности и эксплуатации

-   **HTTPS**: Всегда запускайте VaultN8N за обратным прокси (например, Nginx, Traefik), который обеспечивает HTTPS.
-   **Сетевая изоляция**: Ограничьте доступ к API VaultN8N только для доверенных сервисов (например, n8n).
-   **Управление ключами**: `ENCRYPTION_KEY` и `AUTH_TOKEN` в файле `.env` должны быть надежно защищены.
-   **Резервное копирование**: Регулярно создавайте резервные копии файла базы данных (`secrets.db`).
